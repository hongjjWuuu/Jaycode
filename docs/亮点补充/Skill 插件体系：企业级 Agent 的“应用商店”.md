
## 一、核心概念：Skill ≠ 普通工具

### 概念区分

|类型|定义|粒度|安全控制位置|
|---|---|---|---|
|**普通函数/工具**|Agent 直接调用的 API，如 `search_web()`|细粒度|调用层|
|**Skill（技能）**|可复用的能力单元，封装完成某类任务的完整逻辑|粗粒度|贯穿生命周期|

### Skill 示例

以“代码审查”为例：

- **普通做法**：写一段提示词扔给 AI
    
- **Skill 做法**：封装成一个标准能力包，包含：
    
    - 详细的提示词指令
        
    - 可选的执行脚本（自动下载代码、运行检查工具）
        
    - 内置测试用例（用有 bug 的代码验证审查结果是否正确）
        

任何 Agent、任何工作流需要“代码审查”能力时，直接安装该 Skill 即可复用。

## 二、Skill 分类：基于风险分级的安全设计

### 分类对比

|类型|本质|风险等级|示例|
|---|---|---|---|
|**Prompt Skill**|纯文本提示词模板（SKILL.md）|极低|“用 Google 代码规范审查这段代码”|
|**Code Skill**|可执行 Python 脚本|高|自动 clone 仓库并运行 pylint|

### Prompt Skill（提示词技能）

- 仅包含 `SKILL.md` 文本文件
    
- 加载到 AI 上下文，影响回答
    
- **不执行任何外部代码**
    
- 安全风险几乎为零
    

示例：

你是一个资深代码审查专家。请按照以下标准审查用户提供的代码：
1. 检查 SQL 注入风险
2. 检查变量命名规范
3. 给出修改建议

### Code Skill（代码技能）

- 包含 SKILL.md + Python 脚本
    
- 可调用系统资源：下载代码、运行工具、读写文件、发送网络请求
    
- 可在服务器上执行任意 Python 代码
    
- **安全风险极高**
    

**核心原则：能用 Prompt 解决的，绝不开 Code 的口子。**

## 三、Code Skill 的两层安全控制（纵深防御体系）

### 第一层：权限分级（声明式）

开发者在编写 Code Skill 时必须显式声明所需权限：

|权限等级|允许操作|典型应用场景|
|---|---|---|
|`safe`|纯计算，禁止文件/网络操作|数据处理、数值计算|
|`project_read`|读取项目文件|代码审查、静态分析|
|`network`|访问外网 API|调用第三方服务、下载依赖|
|`filesystem_write`|写入文件|生成报告、修改代码|

**运行时沙箱配置 = 代码声明 ∩ 平台策略（取交集）**

### 第二层：Docker 沙箱（强制执行）

无论 Skill 声明了什么权限，最终都在 Docker 容器内执行：

|安全配置|作用|防范风险|
|---|---|---|
|`--network none`|切断网络连接|防止数据外传、SSRF 攻击|
|文件系统只读|禁止写入/修改/删除|防止恶意篡改|
|限制 CPU/内存/进程数|资源上限控制|防止 DoS 资源耗尽|
|执行完毕自动销毁|删除临时容器|防止残留垃圾/敏感数据|

**两层关系：权限分级是“君子协定”，Docker 沙箱是“法律制裁”。**

## 四、审批模型：身份与意图的解耦

### 设计核心

解决 **“测试通过 ≠ 生产可用”** 的授权问题。

### 两条独立审批线

|调用场景|身份主体|特点|审批要求|
|---|---|---|---|
|`skill_console`（手动测试）|具体用户|有人实时观察，可及时干预|门槛较低|
|`workflow_runner`（自动化流程）|工作流进程|无人值守，全自动执行|更严格审批|

### 审批唯一键机制

**审批唯一键 = `skill_code` + `agent_code`**

含义：同一个 Skill 被不同 Agent 在不同场景调用时，需分别独立审批。

### 典型场景示例

某个“一键部署生产环境”的 Code Skill：

- **手动测试**：用户在控制台手动运行，可实时判断异常并停止 → 审批门槛较低
    
- **工作流自动执行**：代码提交后自动触发，无人值守 → 必须再次审批且更严格
    

**类比：普通驾照（手动测试审批）≠ 大货车驾照（工作流自动审批）**

## 五、全生命周期管理

让 Skill 从“一次性脚本”升级为“可管理的软件制品”：

|能力|说明|
|---|---|
|**版本快照**|每次变更全量存档，可回溯任意时间点的 Skill 版本|
|**升级对比**|新旧版本 Diff 对比，审批人可查看具体变更（含权限变化）|
|**回滚**|新版本故障时一键切回稳定版本，业务不中断|
|**依赖校验**|提前检查沙箱环境是否满足 Skill 的依赖要求|
|**内置测试用例**|Skill 自带输入/期望输出，上线前自动验证（Skill 的“单元测试”）|

## 六、全景运转流程


开发 → 审批 → 授权 → 运行 → 监控与更新

1. **开发**：创建 Skill，声明类型（Prompt/Code）和权限，编写代码及内置测试
    
2. **审批**：部署触发审批流程，审批人查看版本对比及自动测试结果
    
3. **授权**：审批通过后配置调用许可（手动控制台 / 工作流自动调用），两种许可独立颁发
    
4. **运行**：Agent 或工作流触发 Skill 调用，Code Skill 按权限声明启动匹配的 Docker 沙箱执行
    
5. **监控与更新**：运行日志、错误、测试结果持续反馈；新版本走相同审批流程，支持一键回滚

## 七、设计理念总结

这个 Skill 插件体系实质上是在设计一个**企业级 Agent 的“应用商店”**，核心思想是：

- **不给 Agent 直接调工具，而是给每个能力单元配上完整的生命周期和安全护栏**
    
- **能用 Prompt 解决的问题，绝不开 Code 的口子**
    
- **一旦需要 Code，必须走最严格的安全通道（权限声明 + Docker 沙箱）**
    
- **审批按场景隔离，手动测试通过不等于自动化生产可用**
    
- **全流程可追溯、可对比、可回滚、可测试**
