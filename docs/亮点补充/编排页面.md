
编排页你可以把它理解成“流程编辑器 + 节点参数面板”。

先说最重要的一点：

- 左边的“节点库”负责“放什么节点”
- 中间画布负责“节点怎么连”
- 右边的“节点配置”负责“这个节点具体怎么执行”

也就是说，编排页不是只画图，它是在定义一个可执行的 Workflow。

---

**一、节点库里的节点都是什么**

目前节点库里常见的是这些：

- `Planner`
- `Project Agent`
- `Code Review`
- `File Review`
- `RAG Processor`
- `Knowledge Query`
- `MCP Tool`
- `Skill`
- `Supervisor`
- `Human Review`
- `Reporter`

我按“它们各自负责什么”讲：

- `Planner`
    
    - 负责先规划流程
    - 一般不需要复杂配置
    - 适合作为起点
- `Project Agent`
    
    - 负责项目级分析
    - 常用于看目录结构、架构、模块关系
    - 通常配 `agent_type=project_analyzer`
- `Code Review`
    
    - 负责代码审查
    - 适合看风险、质量问题、建议
    - 通常也是 `agent`，但 `agent_type=code_reviewer`
- `File Review`
    
    - 只看单个文件
    - 适合精读一个文件
    - 配置里通常要填 `file_path`
- `RAG Processor`
    
    - 负责把分析结果、文件内容、结论加工进知识库
    - 通常用于沉淀项目知识
    - 可以配置是否 `ingest`，以及写入哪个 `collection`
- `Knowledge Query`
    
    - 负责从 RAG 知识库检索
    - 输入一个问题，返回相关知识片段
    - 主要配 `collection` 和 `top_k`
- `MCP Tool`
    
    - 负责调用外部工具
    - 比如文件系统、git、或真实 MCP server 暴露的工具
    - 重点是 `tool_name`、`server_id`、`agent_code`
- `Skill`
    
    - 负责调用一个具体技能
    - 比如代码审查、RAG 切片、搜索、扫描
    - 核心配置是 `skill_code` 和 `agent_code`
- `Supervisor`
    
    - 负责汇总、判断、协调
    - 适合放在多个分支执行后做总控
- `Human Review`
    
    - 负责人工审核
    - 流程会在这里停住，等你 approve/reject/revise
- `Reporter`
    
    - 负责最终汇总结果
    - 通常放在最后

---

**二、右侧节点配置面板的通用项**

不管什么节点，先有这些通用配置：

- `名称`
    
    - 节点显示名称
    - 会出现在画布、事件流、输出里
    - 比如改成 `项目审查`、`单文件审查`、`知识沉淀`
- `类型`
    
    - 节点执行类别
    - 决定这个节点走哪个运行器
    - 目前可选：
        - `planner`
        - `agent`
        - `rag`
        - `mcp_tool`
        - `skill`
        - `supervisor`
        - `human_review`
        - `reporter`
- `分析重点`
    
    - 给节点一个额外关注点
    - 比如：
        - `结构`
        - `风险`
        - `测试`
        - `依赖`
        - `学习路径`
- `输出要求`
    
    - 约束节点最后产出什么样的结果
    - 比如：
        - `列出风险等级和建议`
        - `输出 Markdown 总结`
        - `输出结构化 JSON`

**三、各类节点配置怎么理解**

### 1. `agent` 节点

这是最复杂的一类，因为它会根据 `agent_type` 变成不同能力。

可选的 `agent_type`：

- `project_analyzer`
    
    - 项目分析
    - 适合看目录、模块、架构、依赖关系
- `code_reviewer`
    
    - 代码审查
    - 适合找 bug、风险、坏味道、优化点
- `file_reviewer`
    
    - 单文件审查
    - 适合只看一个文件
- `rag_processor`
    
    - RAG 处理
    - 适合把资料入库、整理成知识
- `learning_coach`
    
    - 学习陪练
    - 适合帮助理解项目

#### `agent` 常见配置

- `agent_type`
    
    - 决定具体调用哪个子能力
- `max_files`
    
    - 项目分析时最多扫描多少文件
    - 只对项目级分析类 agent 常用
- `max_chars`
    
    - 单文件读取字符数上限
    - 通常 `file_reviewer` 会用
- `file_path`
    
    - 单文件路径
    - 只有 `file_reviewer` 最常用
- `ingest`
    
    - 是否把结果入库到知识库
    - `rag_processor` 常用
- `collection`
    
    - 写入的知识集合名
    - 常见默认值是 `project-memory`

#### 怎么选

- 看整个项目，选 `project_analyzer`
- 看单个文件，选 `file_reviewer`
- 想沉淀知识，选 `rag_processor`
- 想让系统教你怎么理解项目，选 `learning_coach`

---

### 2. `rag` 节点

这是知识检索节点。

#### 配置项

- `collection`
    
    - 要检索的知识库集合名
    - 比如 `project-memory`、`default`
- `top_k`
    
    - 返回最相关的条数
    - 一般 3 到 5 就够用

#### 怎么用

适合放在流程里做：

- 项目知识查询
- 结论补充
- 历史资料检索

#### 容易填错的地方

- `collection` 和你实际入库的集合名不一致
- `top_k` 太大，结果会很杂
- 问题写得太泛，检索效果会差

---

### 3. `mcp_tool` 节点

这是外部工具调用节点。

#### 配置项

- `tool_name`
    
    - 工具名
    - 比如：
        - `filesystem.list`
        - `filesystem.read`
        - `git.status`
        - `git.log`
        - 真实 MCP server 暴露的工具名
- `server_id`
    
    - 真实 MCP server 的 ID
    - `JAYCODE_MCP_PROVIDER=mcp` 时通常必填
- `agent_code`
    
    - 调用身份
    - 审批是按这个身份判断的
    - 默认常见是 `workflow_runner`
- `arguments`
    
    - 传给工具的参数
    - 是 JSON 对象

#### `arguments JSON` 怎么理解

这个地方最容易卡住。

比如：

```
{
  "root_path": "F:/JayAgent/Jaycode",
  "file_path": "app/main.py",
  "limit": 20
}
```

意思就是调用工具时把这些参数传进去。

#### 怎么用

- 想列目录
- 想读文件
- 想调用 git
- 想调用真实 MCP 工具

#### 容易填错的地方

- `tool_name` 拼错
- `server_id` 没填
- `agent_code` 没审批
- `arguments` 不是合法 JSON

---

### 4. `skill` 节点

这是最有治理感的一类节点。

#### 核心配置

- `skill_code`
    
    - 技能编码
    - 比如 `code.review`、`rag.chunk`、`security.scan`
- `agent_code`
    
    - 调用身份
    - 很重要，因为审批是按
        - `skill_code`
        - `agent_code`  
            一起判断的
- `input`
    
    - 直接传给技能的输入 JSON
- `input_mappings`
    
    - 把上游节点的数据映射给 Skill
    - 这部分通常最容易复杂

#### 右侧审批块为什么会出现

因为 `Skill` 节点不是随便就能跑的。

页面里会显示：

- 当前 Skill 是否已审批
- 当前 `skill_code / agent_code`
- 是否允许 Workflow 自动执行

#### 最容易混淆的点

你在页面里会看到两个身份：

- `skill_console`
    - 代表技能页面里手动测试调用
- `workflow_runner`
    - 代表 Workflow 里自动执行

这两个身份审批是分开的。

也就是说：

- 你手动测试通过，不代表 Workflow 自动能跑
- Workflow 还得审批 `workflow_runner`

#### 怎么用最稳

如果你在 Workflow 里加 Skill，通常这样配：

- `skill_code`：要执行的技能
- `agent_code`：`workflow_runner`
- `input`：按需要给业务参数
- `input_mappings`：把上游结果接进来

---

### 5. `human_review` 节点

这是人工审核节点。

#### 配置项

- `require_comment`
    - 是否强制填写审核意见

#### 作用

- 任务跑到这里会暂停
- 等你人工批准
- 批准后再继续执行

#### 适合放在哪里

- 高风险操作前
- 外部工具调用前
- 关键结论确认前
- 生成最终报告前

---

### 6. `planner` 节点

这是流程规划节点。

#### 配置上通常很轻

一般默认就够了。

#### 作用

- 生成执行策略
- 决定后续节点走法
- 作为 Workflow 起点最常见

#### 常见用法

- `Planner -> Agent -> Human Review -> Reporter`
- `Planner -> Agent -> RAG -> Reporter`

---

### 7. `supervisor` 节点

这是总控节点。

#### 作用

- 汇总多个节点结果
- 决定流程是否继续
- 帮助做最终判断

#### 适合场景

- 多分支 Workflow
- 多 Agent 协作
- 需要统一裁决的时候

---

### 8. `reporter` 节点

这是收尾节点。

#### 作用

- 汇总前面节点的输出
- 生成最终报告
- 输出面向用户的结果

#### 通常放哪里

- Workflow 最后
- 或者关键分支汇总后

---

**四、配置区下面那些“Production”项是什么意思**

这部分很重要，因为它决定节点怎么跑。

### `节点执行前人工确认`

- 勾上后，运行到这个节点前会停一下
- 会保存 checkpoint
- 需要你确认后才继续

适合：

- 风险节点
- 重要修改前
- 外部工具调用前

---

### `retry_count`

- 节点失败后自动重试次数
- 0 表示不重试
- 一般建议别太大，最多 3 到 5

适合：

- 网络不稳定
- MCP 调用偶发失败
- 轻微模型波动

---

### `input_from`

这个是告诉节点“输入从哪来”。

常见值：

- `current`
- `goal`
- 上游节点 id

例子：

- `current`：用当前节点上下文
- `goal`：用任务目标
- `plan`：从上游 `plan` 节点取输出

---

### `input_path`

从输入对象里取哪个字段。

例子：

- `report_markdown`
- `results.0.content`
- `plan.0`
- `summary.risk_level`

它和 `input_from` 经常一起用：

- `input_from` 决定来源
- `input_path` 决定取哪个字段

---

### `output_key`

当前节点输出保存到哪里。

默认一般用节点自己的 id。

比如：

- `plan` 节点输出保存成 `plan`
- `review` 节点输出保存成 `review`

后面节点就可以通过这个 key 引用。

---

### `fail_strategy`

节点失败后流程怎么办。

可选：

- `halt`
    - 停止流程
- `continue`
    - 记录失败但继续执行

#### 怎么选

- 重要节点用 `halt`
- 非关键辅助节点可以用 `continue`

---

**五、节点配置之间最容易混淆的关系**

### 1. `agent_type` 和 `type`

这是两层概念，不是一回事。

- `type`
    
    - 决定节点属于什么大类
    - 比如 `agent`、`skill`、`rag`
- `agent_type`
    
    - 只在 `type=agent` 时存在
    - 决定这个 agent 具体做什么

---

### 2. `skill_code` 和 `agent_code`

这两个经常一起出现，但作用不同：

- `skill_code`
    - 你要调用哪个技能
- `agent_code`
    - 谁在调用这个技能

审批就是按这两个字段一起判断的。

---

### 3. `tool_name` 和 `server_id`

- `tool_name`
    - 具体调用哪个工具
- `server_id`
    - 这个工具来自哪个 server

如果是本地模式，有时候 `tool_name` 就够了。  
如果是真实 MCP，则通常两个都要对上。

---

### 4. `input` 和 `input_mappings`

- `input`
    - 直接给技能的输入
- `input_mappings`
    - 把上游节点输出映射进去

简单理解：

- `input` 是“你手工给的”
- `input_mappings` 是“从前一个节点接来的”

---

### 5. `collection` 在不同节点里不是同一个意思

- `rag` 节点里的 `collection`
    - 用于查询知识库
- `rag_processor` 节点里的 `collection`
    - 用于写入知识库

这两个都叫 `collection`，但一个是读，一个是写。

---

**六、一个最实用的配置例子**

如果你现在要做“项目分析 + 审核 + 报告”，最稳的流程是：

### 节点 1：Planner

- `type=planner`
- 基本不用复杂配置

### 节点 2：Project Agent

- `type=agent`
- `agent_type=project_analyzer`
- `max_files=100`
- `focus=架构和核心模块`
- `output_format=列出风险和建议`

### 节点 3：Human Review

- `type=human_review`
- `require_comment=true`

### 节点 4：Reporter

- `type=reporter`
- 基本默认即可

这个流程适合第一次使用。

---

**七、如果你要做“知识沉淀”**

建议这样：

### 节点 1：Planner

### 节点 2：Project Agent

- `agent_type=project_analyzer`

### 节点 3：RAG Processor

- `agent_type=rag_processor`
- `ingest=true`
- `collection=project-memory`

### 节点 4：Reporter

这样会把项目结论沉淀到知识库里，后面追问时就能检索到。

---

**八、如果你要做“代码审查”**

建议这样：

### 节点 1：Planner

### 节点 2：File Review 或 Code Review

- `agent_type=file_reviewer`
    - 填 `file_path`
    - 适合单文件
- `agent_type=code_reviewer`
    - 适合整体代码审查

### 节点 3：Human Review

### 节点 4：Reporter

---

**九、怎么判断一个节点配得对不对**

你可以用这几个问题检查：

- 节点类型和它的职责一致吗
- 输入来源清楚吗
- 输出要给谁用清楚吗
- 需不需要人工确认
- 失败后要停还是继续
- 依赖的审批、权限、集合名是否正确

如果这几个问题能回答清楚，节点一般就配对了。

---

**十、建议你先记住的最关键规则**

1. `type` 决定节点大类
2. `agent_type` 决定具体 agent 角色
3. `skill_code + agent_code` 决定 Skill 审批
4. `tool_name + server_id` 决定 MCP 调用
5. `collection` 在 RAG 里有读写两种用途
6. `input_from` 和 `input_path` 决定节点吃什么输入
7. `fail_strategy` 决定失败后停还是继续
8. `confirm_before_run` 决定是否要人工拦一下
