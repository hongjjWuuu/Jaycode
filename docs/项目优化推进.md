# Jaycode 项目优化推进

## 1. 文档目的

本文用于跟踪 Jaycode 从“本地可运行的 Agent 平台骨架”向“安全、稳定、可维护的任务执行平台”推进的优化工作。

优化项按优先级分为：

- **P0**：上线前必须解决的安全或阻断问题
- **P1**：影响稳定性、可靠性和核心能力质量的问题
- **P2**：结构治理、可维护性和长期工程效率问题

## 2. 当前项目判断

Jaycode 已具备以下基础能力：

- FastAPI API 门户
- LangGraph 固定图和动态 Workflow
- Harness Runtime 任务治理
- SQLite / PgVector RAG
- Memory 长期记忆
- Skill 注册、审批和沙箱执行
- MCP 工具发现、审批和调用
- LLM Trace、Prompt 版本和 Benchmark
- React 可视化工作台

当前主要短板集中在：

- API 和外部能力的安全边界不够强
- 任务执行仍以单进程同步模式为主
- 权限、事务和错误处理缺少统一抽象
- 核心模块测试覆盖不足
- 路由和前端状态过度集中

## 3. P0：上线前必须解决

### P0-1 统一认证与权限体系

**涉及模块：** `app/api/routes/`、`app/harness/policy.py`

**问题：**

- 管理型接口缺少统一认证中间件
- `x_jaycode_actor` 和 `x_jaycode_role` 只能标识请求，不能证明身份
- Skill、MCP、Marketplace、Workflow 和 Memory 的写操作需要更强权限控制

**推进动作：**

- 增加统一认证入口和可信身份上下文
- 建立 user、reviewer、admin、system-agent 角色模型
- 对所有写接口统一增加权限依赖
- 将 actor、role、request_id 写入审计日志
- 对高风险操作强制人工审核或管理员审批

**验收标准：**

- 未认证请求无法访问管理型写接口
- 不同角色的接口权限有自动化测试覆盖
- 审批、执行和删除操作均能追溯到真实主体

### P0-2 Marketplace 远程包安全

**涉及模块：** `app/marketplace/installer.py`

**问题：**

- 支持从任意 HTTP/HTTPS 地址下载包
- ZIP 解压缺少明确的路径穿越防护
- 签名不是强制要求
- 缺少下载大小、解压大小和文件数量限制
- 外部 Skill 可能执行 Python 代码

**推进动作：**

- 生产环境默认关闭任意远程安装
- 增加可信域名白名单或集中式 Registry
- 强制 SHA-256 或签名校验
- 解压前拒绝绝对路径和 `..` 路径
- 增加下载、解压和文件数量上限
- 外部 Python Skill 默认使用 Docker 沙箱
- 安装前增加管理员审批和信任等级

**验收标准：**

- 路径穿越压缩包会被拒绝
- 未签名或签名不匹配的包无法安装
- 超限包无法继续处理
- 外部 Python Skill 不会在 API 主进程中执行

### P0-3 MCP Server 命令执行边界

**涉及模块：** `app/providers/mcp_provider.py`

**问题：**

Real Provider 根据数据库中的 `command` 和 `args` 启动子进程。若配置接口暴露给不可信用户，会形成任意本地命令执行风险。

**推进动作：**

- 仅管理员可保存和修改 MCP Server 配置
- 建立 command 白名单
- 校验 args 和环境变量
- 使用低权限账户运行 MCP Server
- 增加超时、内存、CPU 和进程数限制
- 记录配置者、审批者和实际执行摘要

**验收标准：**

- 非管理员无法写入 MCP Server 配置
- 不在白名单中的 command 会被拒绝
- MCP 子进程超时会被回收
- 每次启动和调用均有审计记录

### P0 实施状态（2026-09-14）

P0 安全闭环已完成：

### P1-1 任务运行后台化和生命周期完善

**涉及模块：** `app/harness/runtime.py`、`app/api/routes/`

**问题：**

- 当前主要通过同步 `graph.invoke()` 执行任务
- 长任务会占用 API Worker
- 缺少真正的队列、取消、超时和幂等机制

**推进动作：**

- 增加任务超时、取消标记和幂等键
- 完善状态：`queued`、`running`、`paused`、`completed`、`failed`、`cancelled`
- 抽象 Worker 接口
- 后续接入 Redis Queue、RQ、Celery 或同类任务队列
- 将 SSE 作为任务事件订阅，而不是同步执行替代品

**验收标准：**

- 重复请求不会重复创建同一任务
- 长任务不会阻塞 API Worker
- 任务可以取消、超时并留下完整状态
- Worker 崩溃后任务可被识别和恢复

### P1-2 任务事件、状态和产物事务一致性

**涉及模块：** `app/harness/runtime.py`、`app/persistence/sqlite_store.py`

**问题：**

任务状态、事件、产物和 checkpoint 分多次写入，中途失败可能造成部分持久化。

**推进动作：**

- 将状态变更和关键事件封装为事务操作
- 为事件增加唯一键和序号
- 增加任务执行版本和恢复次数
- 区分任务事实状态与事件历史
- 对恢复、重试和重复事件增加幂等处理

**验收标准：**

- 状态与最终事件一致
- 重试不会产生不可区分的重复事件
- 任务失败时仍能获取失败原因和恢复信息

### P1-3 SQLite 并发能力增强

**涉及模块：** `app/persistence/sqlite_store.py`

**推进动作：**

- 启用 WAL
- 设置 `busy_timeout`
- 开启外键约束
- 为任务、事件、日志和 Benchmark 增加索引
- 统一事务封装
- 明确 SQLite 仅适用于单机或低并发场景
- 生产环境提供 PostgreSQL 持久化方案
