# Jaycode 项目优化推进

## 1. 文档目的

本文用于跟踪 Jaycode 从“本地可运行的 Agent 平台骨架”向“安全、稳定、可维护的任务执行平台”推进的优化工作。

优化项按优先级分为：

- **P0**：上线前必须解决的安全或阻断问题
- **P1**：影响稳定性、可靠性和核心能力质量的问题
- **P2**：结构治理、可维护性和长期工程效率问题

## 2. 当前项目判断

Jaycode 已具备以下基础能力：

- FastAPI API 门户
- LangGraph 固定图和动态 Workflow
- Harness Runtime 任务治理
- SQLite / PgVector RAG
- Memory 长期记忆
- Skill 注册、审批和沙箱执行
- MCP 工具发现、审批和调用
- LLM Trace、Prompt 版本和 Benchmark
- React 可视化工作台

当前主要短板集中在：

- API 和外部能力的安全边界不够强
- 任务执行仍以单进程同步模式为主
- 权限、事务和错误处理缺少统一抽象
- 核心模块测试覆盖不足
- 路由和前端状态过度集中

## 3. P0：上线前必须解决

### P0-1 统一认证与权限体系

**涉及模块：** `app/api/routes.py`、`app/harness/policy.py`

**问题：**

- 管理型接口缺少统一认证中间件
- `x_jaycode_actor` 和 `x_jaycode_role` 只能标识请求，不能证明身份
- Skill、MCP、Marketplace、Workflow 和 Memory 的写操作需要更强权限控制

**推进动作：**

- 增加统一认证入口和可信身份上下文
- 建立 user、reviewer、admin、system-agent 角色模型
- 对所有写接口统一增加权限依赖
- 将 actor、role、request_id 写入审计日志
- 对高风险操作强制人工审核或管理员审批

**验收标准：**

- 未认证请求无法访问管理型写接口
- 不同角色的接口权限有自动化测试覆盖
- 审批、执行和删除操作均能追溯到真实主体

### P0-2 Marketplace 远程包安全

**涉及模块：** `app/marketplace/installer.py`

**问题：**

- 支持从任意 HTTP/HTTPS 地址下载包
- ZIP 解压缺少明确的路径穿越防护
- 签名不是强制要求
- 缺少下载大小、解压大小和文件数量限制
- 外部 Skill 可能执行 Python 代码

**推进动作：**

- 生产环境默认关闭任意远程安装
- 增加可信域名白名单或集中式 Registry
- 强制 SHA-256 或签名校验
- 解压前拒绝绝对路径和 `..` 路径
- 增加下载、解压和文件数量上限
- 外部 Python Skill 默认使用 Docker 沙箱
- 安装前增加管理员审批和信任等级

**验收标准：**

- 路径穿越压缩包会被拒绝
- 未签名或签名不匹配的包无法安装
- 超限包无法继续处理
- 外部 Python Skill 不会在 API 主进程中执行

### P0-3 MCP Server 命令执行边界

**涉及模块：** `app/providers/mcp_provider.py`

**问题：**

Real Provider 根据数据库中的 `command` 和 `args` 启动子进程。若配置接口暴露给不可信用户，会形成任意本地命令执行风险。

**推进动作：**

- 仅管理员可保存和修改 MCP Server 配置
- 建立 command 白名单
- 校验 args 和环境变量
- 使用低权限账户运行 MCP Server
- 增加超时、内存、CPU 和进程数限制
- 记录配置者、审批者和实际执行摘要

**验收标准：**

- 非管理员无法写入 MCP Server 配置
- 不在白名单中的 command 会被拒绝
- MCP 子进程超时会被回收
- 每次启动和调用均有审计记录

### P0 实施状态（2026-09-14）

已完成第一轮安全封口：

- `app/core/security.py` 提供 API Key、RBAC、统一错误响应、`X-Request-ID` 和安全审计中间件。
- SQLite 新增 `security_audit_log`，MCP 调用日志补充 request、actor、role、命令摘要和退出码字段。
- Marketplace 默认关闭远程源，远程源要求 HTTPS、Host 白名单和 SHA-256 签名；ZIP 具备路径、文件数、解压大小和特殊文件保护。
- 外部 Python Skill 在 Docker 沙箱不可用时拒绝执行，不再降级到 API 主进程 subprocess。
- MCP stdio Server 仅允许配置白名单 command，禁止 shell 风格参数和受保护环境变量覆盖；子进程具备超时、输出上限和 terminate/kill 回收。
- `.env.example` 已补充 P0 配置。开发环境必须显式设置 `JAYCODE_AUTH_ENABLED=false`，生产环境必须配置 API Key 并保持认证开启。

待环境依赖恢复后执行完整 FastAPI、pytest、前端构建和接口回归；当前已完成 Python 语法级检查及 P0 单元测试代码补充。

## 4. P1：稳定性和核心质量

### P1-1 任务运行后台化和生命周期完善

**涉及模块：** `app/harness/runtime.py`、`app/api/routes.py`

**问题：**

- 当前主要通过同步 `graph.invoke()` 执行任务
- 长任务会占用 API Worker
- 缺少真正的队列、取消、超时和幂等机制

**推进动作：**

- 增加任务超时、取消标记和幂等键
- 完善状态：`queued`、`running`、`paused`、`completed`、`failed`、`cancelled`
- 抽象 Worker 接口
- 后续接入 Redis Queue、RQ、Celery 或同类任务队列
- 将 SSE 作为任务事件订阅，而不是同步执行替代品

**验收标准：**

- 重复请求不会重复创建同一任务
- 长任务不会阻塞 API Worker
- 任务可以取消、超时并留下完整状态
- Worker 崩溃后任务可被识别和恢复

### P1-2 任务事件、状态和产物事务一致性

**涉及模块：** `app/harness/runtime.py`、`app/persistence/sqlite_store.py`

**问题：**

任务状态、事件、产物和 checkpoint 分多次写入，中途失败可能造成部分持久化。

**推进动作：**

- 将状态变更和关键事件封装为事务操作
- 为事件增加唯一键和序号
- 增加任务执行版本和恢复次数
- 区分任务事实状态与事件历史
- 对恢复、重试和重复事件增加幂等处理

**验收标准：**

- 状态与最终事件一致
- 重试不会产生不可区分的重复事件
- 任务失败时仍能获取失败原因和恢复信息

### P1-3 SQLite 并发能力增强

**涉及模块：** `app/persistence/sqlite_store.py`

**推进动作：**

- 启用 WAL
- 设置 `busy_timeout`
- 开启外键约束
- 为任务、事件、日志和 Benchmark 增加索引
- 统一事务封装
- 明确 SQLite 仅适用于单机或低并发场景
- 生产环境提供 PostgreSQL 持久化方案

**验收标准：**

- 并发任务写入不产生频繁锁错误
- 任务、事件、产物和日志关系可通过外键校验
- 高频列表接口支持分页

### P1-4 Workflow 校验和类型契约

**涉及模块：** `app/graphs/workflow_compiler.py`、`app/schemas/studio.py`

**问题：**

- 循环、孤立节点和缺少 reporter 目前主要是 warning
- 节点输入输出多为 `dict[str, Any]`
- 输入映射错误通常要到运行时才发现

**推进动作：**

- 区分 error、warning、info 三类校验结果
- 无法终止的循环、缺少节点引用和未审批高风险节点阻止执行
- 为每种节点定义输入输出 schema
- 编译前校验字段映射和类型
- 事件中记录节点输入摘要、输出摘要和校验结果

**验收标准：**

- 非法 Workflow 无法编译
- 字段映射错误在运行前返回
- 高风险节点没有审批时无法执行
- 条件分支和循环都有测试覆盖

### P1-5 RAG 和 Memory 治理增强

**涉及模块：** `app/persistence/rag_store.py`、`app/persistence/memory_store.py`

**推进动作：**

- 按 Python、TypeScript、Markdown 等类型进行结构化切分
- 保存符号名、模块名、行号和文件元数据
- 增加 embedding 模型版本
- 统一 RAG 和 Memory 的 actor、scope、role 权限上下文
- 记录 Memory 来源、用户确认和脱敏结果
- 将 Gold Set 评测纳入 CI

**验收标准：**

- 文档增量更新不会破坏历史版本
- ACL 在查询和列表接口中一致生效
- Memory 冲突、确认、过期和删除均可追溯
- RAG Recall@K、MRR 等指标可重复计算

### P1-6 LLM 结果可信度和失败治理

**涉及模块：** `app/providers/llm_provider.py`、`app/benchmark_runner.py`

**推进动作：**

- 对所有结构化 LLM 输出使用 Pydantic schema 校验
- 强制记录模型、Prompt 版本、fallback、延迟和 token usage
- 报告中明确区分 LLM 结果和规则结果
- 高风险结论不得仅凭 fallback 自动通过
- JSON 解析失败时记录告警，不静默吞掉原因
- 明确模型配置、Agent 覆盖和 Prompt 覆盖的优先级

**验收标准：**

- 结构化输出不符合 schema 时任务状态可识别
- fallback 使用比例可统计
- 高风险结论能追溯模型和 Prompt 版本
- LLM 失败不会导致错误结果被标记为正常结果

## 5. P2：工程结构和长期维护

### P2-1 拆分后端路由和 Service 层

**涉及模块：** `app/api/routes.py`

当前路由文件包含约 90 个接口，建议按领域拆分：

```text
app/api/routes/
  tasks.py
  workflows.py
  rag.py
  skills.py
  mcp.py
  benchmarks.py
  learning.py
```

推荐调用结构：

```text
Route
  -> Service
  -> Graph / Provider
  -> Repository
```

收益：

- 权限逻辑集中管理
- API 测试更轻量
- CLI 和后台 Worker 可复用业务逻辑
- 事务和错误处理更容易统一

### P2-2 拆分前端工作台

**涉及模块：** `web/src/App.tsx`

建议拆分为：

```text
web/src/pages/
  RunPage.tsx
  WorkflowPage.tsx
  ReportsPage.tsx
  ChatPage.tsx
  LlmPage.tsx
  McpPage.tsx
  SkillsPage.tsx
  MarketplacePage.tsx
  BenchmarkPage.tsx

web/src/components/
web/src/hooks/
web/src/services/
```

拆分目标：

- 降低页面之间的状态耦合
- 缩小单次修改影响范围
- 提升组件测试和复用能力
- 让 API 状态和页面状态边界清晰

### P2-3 统一错误模型和可观测性

建议统一返回：

```json
{
  "error_code": "WORKFLOW_VALIDATION_FAILED",
  "message": "Workflow definition is invalid.",
  "request_id": "...",
  "details": {}
}
```

同时补充：

- request_id / task_id / trace_id 贯通
- 结构化日志
- 错误分类统计
- Provider、Workflow、Skill、MCP 的延迟指标
- 关键失败告警

### P2-4 完善测试和 CI

建议新增测试：

- RAG 增量入库、版本、ACL、Gold Set
- Memory 冲突、确认、过期和权限
- Workflow 循环、条件边、重试和恢复
- Skill 合约、审批、禁用和 Sandbox
- MCP 路径越界、审批、超时和进程回收
- Marketplace ZIP 路径穿越、签名失败和包大小限制
- LLM fallback、结构化输出和 Trace
- API 权限矩阵

CI 建议流程：

```text
ruff
  -> pytest
  -> TypeScript check
  -> frontend build
  -> legacy-marker scan
  -> dependency/security scan
```

## 6. 推荐推进顺序

### 阶段一：安全封口

- 完成认证和 RBAC
- 限制 Marketplace 来源和包内容
- 限制 MCP 命令执行
- 统一高风险操作审批

### 阶段二：任务可靠性

- 增加任务幂等、取消、超时
- 统一事务和事件序号
- 优化 SQLite 并发设置
- 完善 Workflow 校验和节点契约

### 阶段三：能力质量

- 加强 RAG 切分和评测
- 统一 Memory 权限和来源治理
- 强化 LLM 结构化输出与 fallback 标记
- 补齐核心测试

### 阶段四：工程化重构

- 拆分后端路由和 Service
- 拆分前端页面和状态模块
- 建立统一错误模型、日志和指标
- 接入 CI、安全扫描和后台 Worker

## 7. 统一验收标准

项目完成本轮优化后，应满足：

- 高风险 API 有认证、授权和审计
- 外部包和 MCP 命令具备明确安全边界
- 任务支持可追踪、可取消、可恢复和幂等执行
- Workflow 在执行前完成结构和类型校验
- RAG、Memory、Skill、MCP、LLM 的关键行为有测试覆盖
- 前后端构建和静态检查纳入 CI
- 文档、默认配置和实际运行环境保持一致
